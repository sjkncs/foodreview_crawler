# 你用的 Coding Agent，是个"助手"还是"代理"？
——从三层架构看懂 Codex 的技术路线

**作者：某 SaaS 团队技术负责人** | **工具：腾讯 QClaw + OpenAI Codex**

注意：腾讯 QClaw 官网下载入口：http://qclaw.qq.com

---

## 先说结论：Codex 不是另一个 AI 编程助手

我用过的 AI 编程工具不算少。从最早的 Copilot 补全，到后来各种 Agent，踩过不少坑。最深的感触是：**大多数工具解决的是"写代码"的问题，Codex 解决的是"做完一件工程任务"的问题。**

这不是换个模型、换个 UI 的区别，是底层设计逻辑的根本不同。

---

## 1. 三层架构：AI 编程工具的"原生"与"拼接"之分

理解了这一层，你就知道 Codex 和其他工具的本质区别在哪。

### 1.1 主流的"补丁式"路线

市面上大部分 AI 编程工具走的是这样一条路：

```
编辑器/IDE 里加个插件 → 接上大模型 API → 对话生成代码 → 你手动复制到文件里
```

这条路跑通了快速原型场景，但有两个硬伤：

- **上下文容易断**：聊多了模型就"忘了"之前说过的，经常出现改 A 函数把 B 接口搞坏的情况
- **执行回环靠人**：生成代码 → 你跑测试 → 报错了 → 贴回去 → 重新生成 → 再跑……一个需求经常要来回四五轮

### 1.2 Codex 的"原生"架构

Codex 的做法不是"往 IDE 里塞一个聊天框"，而是从执行链路出发，共同设计了三个层：

| 层 | 职责 | 对应能力 |
|---|------|---------|
| **模型层（Model）** | 代码理解、方案推理、生成 | 能理解整个仓库结构，不只是当前文件；处理架构级问题，不只是函数级改写 |
| **框架层（Harness）** | 把"建议"变成"可执行动作" | 读写文件、运行命令、跑测试、通过上下文压缩和状态管理降低长对话失真 |
| **界面层（Surfaces）** | 适配不同生产场景 | App / CLI / IDE / Cloud 四种形态，同任务可在不同入口接力，不必重建上下文 |

这才是 **Native Coding** 的核心：不是把模型硬塞进旧工具，而是从执行链路开始共同设计整个系统。

### 1.3 为什么 Codex 经常"一击必杀"？

不是模型更大。是因为这三层的协同让它可以做到：

1. **先理解全貌再看细节** — 模型层先读仓库结构，理解模块关系，再分析具体代码
2. **自己跑验证** — 框架层让它能自动执行测试、lint、构建，改了代码马上跑结果
3. **长对话不失真** — 上下文压缩 + 状态管理，不会改到后面忘了前面

所以在复杂任务上，Codex 常见表现是**前期思考时间更长，但一次产出质量更高** — 省的是返工的轮次。

### 1.4 能力边界（这段话建议截图保存）

Codex 能做的事：
- 写生产级代码和测试
- 理解复杂仓库结构
- 做代码审查与优化建议
- 诊断错误并给出修复路径
- 自动化重复工程任务

Codex 不能替代的事：
- 业务决策
- 最终安全审计
- Code Owner 的上线把关

**一句话**：它很强，但你仍然要做 Review。把它视为一个有能力的工程执行者，不是替你签字的那个。

## 2. 四种形态（Surfaces）：不同场景下的最佳打开方式

Codex 不是只有一个入口。四种形态各有擅长，选对了效率翻倍。

| 形态 | 适用场景 | 核心优势 | 平台 |
|------|---------|---------|------|
| **App** | 主力开发、并行任务、Git 工作流 | 并行线程、Worktree、内置 Git | macOS（Apple Silicon 优先） |
| **CLI** | 终端、脚本化、CI/CD | 功能完整、可编排、易自动化 | macOS / Linux / Windows |
| **IDE 扩展** | 编辑器内迭代 | 上下文感知、所见即所得 | VS Code / Cursor / Windsurf / JetBrains |
| **Cloud** | 后台长任务、远程执行 | 不占本地、并行能力强、GitHub 集成 | Web |

### 2.1 Codex App：主力开发的正确姿势

App 才是 Codex 的第一形态，不是 CLI。对日常开发来说，App 有两个核心竞争力：

**Worktree 工作流（强烈推荐）**

```
新建线程时选择 Worktree → 设定基线分支（如 main）
→ 执行任务并完成验证 → 将结果转分支并发起 PR
```

好处：**隔离、可并行、低污染**。每个任务独立工作区，不会因为一个任务的代码改动污染另一个。这对并行开发多个 feature 的场景是关键提升。

**三种工作模式对比**

| 模式 | 适合 | 风险 |
|------|------|------|
| Local | 小改动 | 直接改工作区 |
| Worktree | 推荐默认 | 隔离，可并行 |
| Cloud | 重任务、长任务 | 远程执行 |

**Automations（自动化）**

把固定任务变成定时作业：

```
每天凌晨 2 点对 staging 分支做代码审查
每次 release PR 后自动更新 API 文档
日志告警触发后自动生成修复草案
```

⚠️ 关键安全建议：

- 审批策略不要默认全开放
- 沙盒优先 read-only 或 workspace-write
- 关键仓库必须保留人工合并门禁

### 2.2 CLI：批量、可复制、可集成的形态

如果你的场景是"可复制、可批量、可集成"，CLI 是王道。

**三种用法**

```bash
# 交互式
codex "帮我重构这个模块，先输出计划再改代码"

# 非交互脚本化（适合 CI/CD）
codex exec --json "分析这个目录的风险" > result.json
codex exec --output-last-message report.md "生成发布说明"

# 会话续接
codex resume --last
codex fork --last
```

**高频进阶开关**

```bash
--model gpt-5.3-codex            # 模型切换
--config model_reasoning_effort=high  # 推理强度
--image screenshot.png            # 图片输入（支持看图改代码）
--search                          # 网页搜索（需权限约束）
/review                           # 代码审查
```

### 2.3 IDE 扩展：编辑器内闭环

如果你一天 80% 时间在编辑器里，IDE 扩展摩擦最小。

核心价值：
- 自动带入当前文件与选中代码
- `@filename` 精准引用上下文
- 不离开编辑器完成提问、改动、审查

三种审批模式：
- **Chat**：只讨论，不改文件
- **Agent**：默认读写 + 执行命令
- **Agent (Full Access)**：含更高权限

### 2.4 Cloud：后台重任务的归宿

Cloud 适合：
- 仓库级重构（可能跑好几个小时）
- 多模块并行分析
- 需要离线等待结果的任务

工作流：**App/IDE 里选 Cloud → 提交任务 → 离线等待 → 审查 diff → 手动应用到本地**

## 3. 快速决策：你该用哪种形态？

```
终端重度用户 + CI/CD        → CLI
并行多功能 + 强调隔离       → App + Worktree
编辑器内小步高频改代码      → IDE 扩展
跑几个小时的重任务          → Cloud
```

**推荐组合拳**：
- 日常主力：App + IDE
- 自动化链路：CLI + Cloud
- 大型重构：App(Worktree) + Cloud

## 4. 配置系统：把团队标准固化为默认

Codex 的 TOML 配置系统有清晰的优先级链：

```
CLI 参数(--config) > Profile(--profile) > 项目(.codex/config.toml)
 > 用户(~/.codex/config.toml) > 系统配置 > 默认值
```

**项目级推荐配置模板**

```toml
model = "gpt-5.3-codex"
model_reasoning_effort = "high"
approval_policy = "on-request"
sandbox_mode = "workspace-write"
web_search = "cached"

developer_instructions = """
这是一个 FastAPI 项目。
请优先保持现有目录结构。
所有新增函数必须有类型注解和测试。
"""

[history]
persistence = "save-all"
max_bytes = 104857600
```

这套配置的价值在于：**把团队的代码规范变成 Codex 每次执行时自动遵守的默认约束**，不用每次下任务都重复强调。

## 5. 提示词工程：Codex 懂你，但你需要说清楚

### 5.1 差异一目了然

```
❌ 坏提示词：帮我写个程序

✅ 好提示词：用 Python 写一个异步 HTTP 客户端
1) 支持 GET/POST/PUT/DELETE
2) 默认超时 30 秒
3) 自动重试 3 次，指数退避
4) 记录请求/响应日志
5) 使用 aiohttp
```

### 5.2 万能公式（直接套用）

```
目标：    你要达成什么
技术栈：  语言/框架/库
输入：    文件/接口/数据来源
输出：    产物和格式
约束：    不可改动内容、性能、安全、兼容性
质量要求：测试、类型注解、文档、错误处理
```

### 5.3 迭代式推进（最实用的策略）

不是一次性把需求全堆进去，而是分三轮：

| 轮次 | 目标 | 产出 |
|------|------|------|
| 第一轮 | 骨架 | 架构 + 最小可运行实现 |
| 第二轮 | 能跑 | 鉴权 + 缓存 + 重试 + 日志 |
| 第三轮 | 强化 | 性能 + 安全 + 可观测性 + 测试 |

## 6. CLI 自动化实战：批量任务与可回滚脚本

这也是 Codex CLI 最被低估的能力之一。

### 6.1 最小目录结构

```
automation/
  tasks.txt          # 每行一个任务描述
  outputs/           # 输出目录
  run.sh             # 执行脚本
```

### 6.2 可回滚的执行脚本

```bash
#!/usr/bin/env bash
set -euo pipefail

mkdir -p automation/outputs
# 先备份上一次的输出结果
cp -r automation/outputs "automation/outputs.bak.$(date +%Y%m%d%H%M%S)"

while IFS= read -r task; do
  [ -z "$task" ] && continue
  safe_name=$(echo "$task" | tr ' /' '__' | cut -c1-60)
  codex run "$task" > "automation/outputs/${safe_name}.md"
done < automation/tasks.txt
```

### 6.3 质量门禁（批量跑完后必查）

1. **输出文件数量是否与任务数量一致**
2. **是否出现空文件或异常短内容**
3. **关键任务是否包含预期字段**

### 6.4 失败处理策略

| 场景 | 策略 |
|------|------|
| 单条任务失败 | 记录行号，继续下一条 |
| 大面积失败 | 回滚到最近一次 outputs.bak.* |
| 持续超时 | 降低并发和任务复杂度 |

## 7. 团队落地路线（直接可用）

### 第一周：打基础
1. 安装 CLI：`npm install -g @openai/codex && codex login`
2. 跑一个简单任务验证链路
3. 在项目目录创建 `.codex/config.toml`

### 第二周：入工作流
1. 日常开发切到 App + Worktree
2. 代码审查固化为 `/review` 指令
3. 把团队的代码规范写进 `developer_instructions`

### 第三周：自动化
1. 建 `automation/tasks.txt` 跑批量任务
2. 把高频重复任务定时化
3. 复盘失败任务，迭代提示词模板

### 长期：体系化
1. 沉淀团队共享 Skills（审查模板、检查清单）
2. MCP 集成第三方上下文（文档、设计系统）
3. 关键仓库设置人工合并门禁

## 8. 用和不用，差距在哪

| 任务 | 传统 AI 编程工具 | Codex（正确使用） |
|------|-----------------|-------------------|
| 小改动（加个函数） | 差不多快 | 差不多快 |
| 中等复杂度（模块重构） | 2-3 轮对话 + 手动跑测 | 1 轮，自动验证，差 2-3 倍 |
| 复杂工程任务（跨模块改动） | 经常跑偏，5+ 轮返工 | 深推理一次到位，差 5 倍以上 |
| 批量重复任务 | 逐条问逐条贴 | 一条批量脚本，差 10 倍 |
| 代码审查 | 手动逐文件看 | `/review` 自动输出审查意见 |
