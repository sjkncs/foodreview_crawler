# Palantir AIP 对本项目的适用性分析

## 结论

Palantir AIP 的思想适合本项目的最终产品形态，但不适合简单照搬其商业平台。

适合借鉴的是：

- 用 Ontology / 对象模型统一业务实体。
- 把 AI 操作限制在有权限、有审计、有安全边界的 Action 中。
- 让用户通过自然语言或任务模板调度底层工作流。
- 将数据、模型、流程和人工审批放在同一个运营闭环中。

不建议直接依赖的是：

- 直接采购或绑定 Palantir AIP 作为本项目技术底座。
- 把它理解为“纯视觉 Agent 托管浏览器”。
- 忽略本项目已经跑通的平台执行器、接口捕获和导出代码。

## 对应关系

| Palantir AIP 思路 | 本项目落地方式 |
|---|---|
| Ontology | `Platform`、`Country`、`Store`、`Review`、`OrderDetail`、`CollectionTask`、`QualityReport` |
| Action | 只读采集、打开订单详情、导出、翻译、质量检查 |
| Guardrails | `SafetyPolicy`：禁止回复、保存、删除、提交 |
| Workflow | 按国家/账号/门店分段运行采集任务 |
| Human-in-the-loop | 登录、验证码、异常页面暂停人工确认 |
| Auditability | 原始 JSON、CSV、错误列表、质量报告、执行日志 |
| AI assistance | 翻译、关键词、情感、视觉导航、异常识别 |

## 推荐产品架构

```text
用户任务
  -> 统一任务 DSL
  -> 安全策略检查
  -> 平台 executor
  -> API/DOM/视觉导航/OCR 混合采集
  -> 标准对象模型
  -> 翻译与情感分析
  -> 质量报告
  -> Dashboard / 导出
```

## 为什么适用

本项目不是单纯爬虫，而是一个跨平台运营数据系统。它需要：

1. 多平台数据接入。
2. 门店、订单、评论、图片、译文的统一对象模型。
3. 只读安全边界。
4. 人工介入登录和验证码。
5. 面向业务用户的任务模板和看板。

这与 AIP 强调的“企业对象模型 + AI 编排 + 安全动作 + 审计”方向一致。

## 为什么不能照搬

本项目目前的核心资产是已经沉淀的平台执行器：

- Hungry Panda、Fantuan、GrabFood、Google Maps 已有实际采集逻辑。
- 订单详情和图片 URL 依赖每个平台的真实页面结构/API。
- 视觉模型只能帮助定位页面，不能保证字段级准确率。

因此最务实的路线是：采用 AIP 式产品架构和对象建模思想，但继续使用本项目自己的 Python 采集框架作为执行底座。

## 最小可用成果形态

面向最终展示，应呈现为：

- 一个任务中心：创建“平台 + 国家 + 门店 + 近 7 天”的采集任务。
- 一个门店覆盖矩阵：显示每个平台哪些店能采、哪些失败。
- 一个评论工作台：评论原文、中文译文、评分、图片 URL、订单详情。
- 一个质量报告：字段完整率、图片覆盖率、订单详情覆盖率、错误门店。
- 一个安全说明：所有后台动作只读，禁止回复/保存/删除/提交。
